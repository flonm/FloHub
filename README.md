# FloHub

> [!WARNING]
> **FloHub is pure AI slop.** Every line of it was generated by an AI coding agent (Claude Code): the code, the tests, the styles and this README. No human wrote it, and no human has reviewed it line by line. It may break whenever GitHub changes its pages, and it is not an example of how anything should be built. Use it at your own risk.

A Chrome, Firefox and Safari extension that adds a Graphite-style overview to every GitHub pull request tab, including the new Files changed view. It shows the stack with each layer's status, plus every reviewer's verdict with one-click re-request.

- **Stack:** GitHub's native stacked PRs, top layer first, down to the base branch. Each layer has a colored badge:
  - purple: merged, or *Merging…* while it waits in the merge queue
  - grey: draft or closed
  - red: merge conflict or failed checks
  - yellow: changes requested, or *Unresolved comments* when it's approved but conversations are still open
  - green: *Ready to merge*, approved with every conversation resolved
  - blue: needs review

  Each row also shows resolved/total conversations and the time since the last push, title or body edit, or review. The current PR is highlighted, and links keep you on the tab you're on. Merged layers fold into one "N merged" row. The whole section collapses to a colored strip, and that setting is remembered. A PR outside any stack shows on its own.

- **One row per reviewer,** in a column beside the stack, most actionable first: *Changes requested*, *Re-requested*, *Review requested*, *Dismissed*, *Commented* and *Approved*. Requested teams get a row too. A glyph says what the reviewer said, in its colour: a green check for an approval, a yellow page with plus and minus for a change request, a speech bubble for a comment. The row's border says what counts now: green or yellow for a standing verdict, grey for none. A dismissed approval keeps its green check inside a grey border. A dashed border means they're asked to review, for the first time or again; a re-requested reviewer whose approval still counts has a green dashed border. The tooltip, and screen readers, say the rest: when they reviewed, what came before a re-request, a recent poke. The row's buttons (re-request, poke, dismiss) appear on hover or keyboard focus. With the stack collapsed, the reviewers shrink to their faces, each with the same glyph and border as a small badge.
- **Poke:** a pointing finger on every reviewer who is currently requested (pending or re-requested), for users and teams. It removes and re-adds the review request, which makes GitHub send them a new notification within about a minute; asking again for a pending reviewer would do nothing. The PR timeline shows it as a removed and a new review request. A poked reviewer shows a grey finger instead of the button for an hour, with the time in the tooltip, remembered per browser. If re-adding fails, FloHub retries once and otherwise tells you to re-request them by hand.
- **Discussion:** the overview lists the comments people leave on the pull request as a whole: the text of each review (with its verdict) and general comments, newest first, with a link to each on GitHub. Inline review threads stay in GitHub's Comments panel. Comments since you last opened the pull request are marked "New", and the list shows those by default. The comment button in the toolbar counts the comments and the new ones, and opens the rest; on a first visit, "since your last review" counts instead. Long comments clamp to three lines with "Show more". Bots and stack tools' comments (CodeRabbit, Graphite's and gh-stack's stack notes) are hidden behind the bot button beside it. Comments keep GitHub's formatting (code, lists, links, quotes, tables, images, task lists and alert boxes), rebuilt from an allowlist so no script, handler or unsafe link reaches the page.
- **Which review counts:** a reviewer's verdict is their latest approval, change request or dismissed review. A later plain comment doesn't override it.
- **What's left out:** the PR author's own replies, unsubmitted drafts, and bots that only commented.
- **Viewed files in the tree:** on the Files changed tab, every file in the file tree gets a checkbox showing your Viewed mark, and clicking it marks or unmarks the file. Viewed files are dimmed, and so is an expanded folder once every file in it is viewed. A file that changed after you viewed it shows an amber dot. When the file's own Viewed checkbox is on the page, the tree clicks that one, so GitHub collapses the diff as usual. Otherwise the change goes through the API.
- **Line counts in the tree:** every file in the Files changed tree shows its added and deleted lines (`+12 −3`), right-aligned next to its Viewed checkbox, including files whose diff isn't rendered. A side with no lines is left out, and a binary file or a pure rename shows none. Hovering the counts spells them out.
- **Instant revisits:** the last overview of each pull request is kept in the extension's local storage for a week, up to 50 pull requests. A revisit shows it at once, marked as refreshing, until GitHub's answer replaces it. A layer you haven't opened yet shows its stack from another layer you opened, with reviewers loading. Changing the token clears the cache.
- **Compare versions after a rebase:** when the branch was force-pushed, the toolbar under the stack says how often, and its switch for what Files changed shows (**GitHub's diff**, **Since vN**, **Versions**) offers **Versions**. It replaces GitHub's diff with a range-diff of the whole pull request between any two of its versions: what the pull request itself changes in each version is diffed against the other, so what the base branch gained in between doesn't show up. It reads like any diff: a line only the newer version has is green, a line only the older one had is red, and where a line replaced a similar one, the words that differ are highlighted. The grey `+` or `−` beside the code, and the two line numbers, are what the pull request itself does to the line, so a line it adds the same way in both versions stays white. TypeScript, JavaScript, JSON and SQL get syntax colors. Folded context expands on click. The view's one-line toolbar picks the two versions: **From** and **To** name each in a few words (`v2 your review`, `v3 current`), and their lists show each version with its tags, its commit, who pushed it, its age, and its reviewers with their verdicts. They open on a click or the down arrow, and the arrows, Enter and Escape work in them. Neither offers a version that would put the newer side before the older. Between them, a strip draws every version from the base branch to the head, the compared range filled in and your last review marked under it. A version someone reviewed gets a wider slot with each reviewer's avatar and their verdict's icon (approved, changes requested, commented); a review since dismissed keeps the verdict it gave, its face greyed out. The many versions nobody reviewed shrink to ticks. Click a version to start the range there, or one past the range to end it there (Shift-click picks the newer side); hover it for its commit, pusher, age and reviews. **Reviews** follows one reviewer: its list shows each reviewer's verdicts version by version, and once you pick one, the strip shows only their reviews. Beside them, **Split** shows the diff side by side, **Comments** shows or hides the review threads, **Wrap** wraps long lines, and an icon opens GitHub's own compare. Each file header shows the diffstat squares, whether the file was renamed, a button to copy its path and a link to the file at that version. Each file says what happened to it between the versions: *Changed*, *New file*, *Deleted*, *Restored*, *Newly changed* or *No longer changed*. A whole new or deleted file drops the markers and line numbers that would only repeat that. Files whose change is the same in both versions are listed collapsed. It ignores hunks that only moved, but conflict resolutions show up. By default it compares the version you last reviewed, or else the previous one, with the current one.

  Versions are the heads before and after every force push, plus every commit someone reviewed. Plain pushes in between aren't recorded anywhere, so they only show up if someone reviewed them. They're numbered in the order they were the head, not by commit date. In a stack, an old version is diffed against the head the base branch had back then, so the parent's old commits don't leak into it. That still holds after the parent is merged and GitHub retargets the pull request. A file GitHub shows no diff for (binary, or too large) is marked *Can't compare* when its content differs, since that may only be the base's doing. GitHub lists at most 300 files per version; past that, files only one version lists are left out.
- **What changed since your review, in GitHub's own diff:** if you reviewed an older version of the pull request, Files changed highlights what is new or different since then, with the same rebase-aware comparison. A changed line gets an amber bar on its left, and you comment on it as usual. Where lines of the version you reviewed are gone, a red marker (`−2`) at the right end of the line before lists them on click (Escape or a click elsewhere closes the list). Each file header says whether the file changed since your review. The switch's **Since vN** counts the files and turns the highlights on; **GitHub's diff** takes them off. A button beside it lists the files the pull request no longer changes. Nothing is highlighted until you've submitted a review of a version older than the current one, and only the whole pull request's Files changed tab is highlighted, not a commit or a range of commits. The highlights are fetched again only when the head, the base or your latest review changes; otherwise they come from storage.
- **Jump to a comment's code:** in GitHub's comments panel on Files changed, a click on a comment's file link opens a small menu instead of GitHub's jump, which doesn't scroll there and sends an outdated comment to a single-commit view. **Changes since vN** opens the versions view from the version the comment was written on to the head, **Code at vN** shows that version's own changes, and **In the current diff** scrolls to the comment's thread or line in the diff on screen, greyed out when the comment is outdated. Each choice has an icon and a number key (1, 2, 3), and arrow keys, Enter and Escape work as in any menu. A modified click (⌘, Ctrl, Shift) still goes to GitHub. See `docs/github-quirks.md`.
- **Inbox:** the toolbar button's popup lists the pull requests waiting for your review, those waiting for their author after your review, and your own, grouped by stack, with the number waiting for you on the button's badge. It checks every 5 minutes. Each row shows the layer's status, the author, the repository, its place in its stack, resolved conversations and size. Rows also show everyone else's latest verdict as faces, each with the verdict's icon (who approved, who wants changes), and hovering them names each one; your own verdict stays a flag on the row. Arrow keys or `j`/`k` move between rows, and Enter opens one.
- **Placement:** the overview sits inline below GitHub's PR header. In GitHub's newer header, that's below the tabs, so the PR number stays on the title's line. Once the header scrolls away, a compact pill appears at the bottom left with the stack strip, layer position and reviewer faces. It expands to the full overview (Escape closes it). The button beside it minimizes the pill to a slim tab at the window's left edge, so it doesn't cover the bottom of a long file tree; FloHub remembers the choice.

## Shortcuts

Graphite's shortcuts, on every pull request tab. They never fire while you type in a text field.

| Keys | Action |
|---|---|
| <kbd>⌘</kbd><kbd>⇧</kbd><kbd>↑</kbd> / <kbd>⌘</kbd><kbd>⇧</kbd><kbd>↓</kbd> (<kbd>Ctrl</kbd> outside macOS) | Go to the pull request above / below in the stack, on the same tab |
| <kbd>R</kbd> then <kbd>Y</kbd> | Approve right away, without a comment |
| <kbd>R</kbd> then <kbd>A</kbd> | Open the approve dialog to add a comment |
| <kbd>R</kbd> then <kbd>N</kbd> | Open the request-changes dialog; the comment is optional |
| <kbd>C</kbd> then <kbd>C</kbd> | Copy `gh pr checkout <number>` |
| <kbd>C</kbd> then <kbd>G</kbd> | Copy the pull request's link |

If you have a pending review with draft comments, every review shortcut submits it, so the drafts go out with your verdict, as with GitHub's "Submit review". In the dialog, <kbd>⌘</kbd><kbd>↵</kbd> submits and <kbd>Esc</kbd> cancels. GitHub refuses a change request without a comment, so an empty one is sent with an invisible zero-width space as its comment, which shows as an empty review.

Since <kbd>C</kbd> starts a FloHub shortcut, GitHub's own <kbd>C</kbd> shortcut (the commits menu on the Files changed tab) doesn't fire on pull request pages. <kbd>R</kbd> still reaches GitHub, so quote-reply on selected text keeps working.

## Install

```bash
bun install
bun run build
```

1. Open `chrome://extensions`, turn on **Developer mode**, click **Load unpacked** and pick `dist/`.

   For Firefox (128 or later), run `bun run build:firefox` instead, open `about:debugging#/runtime/this-firefox`, click **Load Temporary Add-on…** and pick `dist-firefox/manifest.json`. Firefox drops temporary add-ons on restart. To keep it installed, download the signed `.xpi` from the latest [release](../../releases) and open it in Firefox. If the options page says FloHub can't read GitHub, click **Allow access to GitHub**, or allow it under the add-on's **Permissions** in `about:addons`.

   For Safari on macOS, download `flohub-safari-<version>.zip` from the latest [release](../../releases), unzip it, move `FloHub.app` to Applications and run `xattr -dr com.apple.quarantine /Applications/FloHub.app` once, since the app isn't signed with an Apple developer account. To build it yourself instead, run `bun run install:safari` (needs Xcode): it builds the app, copies it to `~/Applications` and opens it. Open the app once, then in Safari turn on **Show features for web developers** under Settings → Advanced, choose **Develop → Allow Unsigned Extensions**, and enable FloHub under Settings → Extensions with `github.com` and `api.github.com` allowed. Safari turns **Allow Unsigned Extensions** off on every restart, so tick it again after relaunching. Safari doesn't update FloHub on its own: install a newer release, or run `bun run install:safari` again.
2. Click the extension's toolbar icon, or "Set up token" in the bar, and paste a token. [This link](https://github.com/settings/tokens/new?description=FloHub&scopes=repo,read:org) creates a classic token with the right scopes, and it needs no organization approval:
   - `repo`: read pull requests, re-request reviews and mark files as viewed
   - `read:org`: show requested teams

   A fine-grained token works too. Choose the organization as resource owner and grant Pull requests: Read and write, Checks: Read, Commit statuses: Read, and optionally Members: Read. The organization may need to approve it. If the token can't read a field, the overview still renders and a notice names what's missing.

After `bun run build`, click the reload icon on the extension's card in `chrome://extensions`. In Firefox, run `bun run build:firefox` and click **Reload** on the add-on in `about:debugging`. In Safari, run `bun run install:safari` again.

ESLint runs typescript-eslint, which needs TypeScript's JavaScript API. TypeScript 7 no longer ships one, so inside ESLint `eslint-typescript.js` resolves `typescript` to TypeScript 6 (the `typescript-eslint-ts` alias). `tsc` and oxlint's type-aware rules use TypeScript 7.

The smoke test runs logged out, so it exercises GitHub's classic PR markup. The bar anchors to the first page heading containing `#<number>` (see `src/ui/anchor.ts`). If a GitHub redesign breaks that, the floating pill still works. Fix the anchor there.

## Release

Firefox only installs signed add-ons for good. FloHub is signed as an *unlisted* add-on: Mozilla signs it automatically, and it doesn't appear on addons.mozilla.org.

To release, tag any commit on `main` as `v<version>` and push the tag, for example `git tag v0.2.0 && git push origin v0.2.0`. The version comes from the tag: one to four dot-separated numbers, higher than the latest release, since AMO never signs the same version twice. `static/manifest.json` stays at `0.0.0`, which marks local builds; `FLOHUB_VERSION=0.2.0 bun run build:firefox` sets a version by hand. A release includes every commit up to the tagged one.

`.github/workflows/release.yaml` then checks the version, signs the Firefox build and builds the Safari app on a macOS runner. Once both succeed, it attaches `flohub-<version>.xpi`, `flohub-safari-<version>.zip` and `updates.json` to the tag's GitHub release: to the one you drafted on GitHub's release page if it exists, otherwise to a new one. The Firefox job runs in the `amo` environment, which holds the `AMO_JWT_ISSUER` and `AMO_JWT_SECRET` secrets, accepts only `v*` tags and waits for a required reviewer's approval. The Safari app is signed for local use only, since a Developer ID signature needs a paid Apple developer account.

The first signature ties the add-on ID in `build.ts` to the AMO account that owns the keys, so every later release must be signed with that account's keys.

Firefox updates FloHub on its own, starting with the first release that includes this update setup (the releases after 0.1.1). The Firefox manifest's `update_url` points at `releases/latest/download/updates.json`, which always resolves to the newest release's `updates.json`. Firefox checks it once a day; **Check for Updates** in `about:addons` checks right away. Installed copies keep that URL for good, so the repository must keep its name and the release assets their names. 0.1.0 and 0.1.1 have no `update_url`: install the next release's `.xpi` once by hand, and later versions arrive on their own.

## Layout

`src/` is split by what a module may touch:

- `src/background.ts`, `src/content.ts`, `src/options.ts`, `src/popup.ts`: the four entry points `build.ts` bundles. They stay at the top, so the manifest and the built file names don't move.
- `src/core/`: pure logic with a return value, no browser API and no DOM: reviewer states, layer statuses, ages, diff marks, the interdiff, version bases, URL parsing, review scope, the raw-tree inbox.
- `src/api/`: everything that talks to GitHub or to the extension's own storage: the service worker's client, the typed messages, the overview cache, the inbox alarm.
- `src/ui/`: the DOM the user sees, in the page, the shadow root and the popup: the bar, the stack, discussion, inbox, review, versions and toast views, and the page helpers (anchor, file tree, diff highlights, favicon).
- `src/styles/`: the design system. `tokens.css` holds every color, font, radius and shadow once (each reading GitHub's Primer variable with a fallback), `base.css` the primitives and the tone palette, `controls.css` the tool buttons, switches and tooltip the bar and the versions view share, `faces.css` a reviewer's face with their verdict, and one file per surface: `bar.css`, `popup.css`, `options.css`. `dark.css` adds the pages' dark fallbacks and is deliberately not part of the bar, which follows GitHub's own theme rather than the machine's.
- `src/stories/`: the Storybook stories. `src/test-gaps.test.ts` walks every folder and fails when a module that builds DOM appears in no story, or another module has no test of its own.

By feature:

- `build.ts`: bundles `src/` and copies `static/` into `dist/` (Chrome) or, with `firefox`, into `dist-firefox/`. The Firefox manifest runs the background script as an event page and adds the add-on ID under `browser_specific_settings.gecko`. Both browsers run the same `chrome.*` code.
- `src/background.ts`: the service worker (an event page in Firefox). It holds the token and makes every API call: one GraphQL query for reviewers and the stack (`PullRequest.stack.entries`), and REST `POST …/requested_reviewers` to re-request, which adds to the existing requests.
- `src/core/versions.ts`, `src/core/interdiff.ts`, `src/ui/versions-dialog.ts`: Compare versions. The versions come from `HeadRefForcePushedEvent`s and reviews' commits, and the base branch's earlier heads from the same-repository pull requests whose head it is, or was (`BaseRefChangedEvent`, `AutomaticBaseChangeSucceededEvent`). Each version is compared (`GET …/compare/<base>...<head>`) with the current base and each candidate, and diffed against the closest one: of the candidates it descends from and its merge base with the current base, the one with the fewest commits in between (`ahead_by`). So an old ancestor, like a release pull request's head in a git-flow repository, can't beat the merge base. `interdiff.ts` pairs the files, strips line numbers from hunk headers, and runs a Myers diff over the two patches. It keeps each line's numbers from the version it comes from, and pairs each removed line with the most similar added one after it for the word highlights. `src/core/diff-marks.ts` maps that diff back to the current diff's lines (`L`/`R` plus line number, as GitHub's line anchors name them), and `src/ui/diff-highlights.ts` marks them on the page. It handles both diffs GitHub serves: the classic one, whose line number cells have `id="diff-<hash>R12"`, and the React one (signed in), whose line number cells have `data-diff-side` and `data-line-number`. In both, the code cell follows its line number cell.
- `src/ui/file-tree.ts`, `src/core/viewed.ts`: the Viewed checkboxes in the file tree. A tree item is matched to its file by the `#diff-<sha256(path)>` anchor or, failing that, by its labels from the root down. Viewed marks and line counts come from `PullRequest.files` (`viewerViewedState`, `additions`, `deletions`), and marks change through `markFileAsViewed`/`unmarkFileAsViewed`.
- `src/content.ts`: follows GitHub's in-page navigation, mounts the bars, and refreshes on focus and on visibility changes.
- `src/core/reviewers.ts`, `src/core/stack.ts`, `src/core/age.ts`: pure derivation of reviewer states, layer statuses and ages from the raw query.
- `src/ui/bar.ts`, `src/ui/stack-view.ts`, `src/ui/dom.ts`, `src/ui/bar-styles.ts`: the Shadow DOM UI. `bar-styles.ts` composes the design system's `tokens.css`, `base.css` and `bar.css` into the style the shadow root injects, themed through GitHub's Primer CSS variables.
- `src/core/shortcuts.ts`, `src/ui/review-dialog.ts`, `src/ui/toast.ts`: the key sequences, the review dialog, and the feedback toast.
