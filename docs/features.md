# FloHub in detail

Everything FloHub does, feature by feature. The [README](../README.md) shows the highlights.

- **Stack:** GitHub's native stacked PRs, top layer first, down to the base branch. Each layer has a colored badge:
  - purple: merged, or *Merging…* while it waits in the merge queue
  - grey: draft or closed
  - red: merge conflict or failed checks
  - yellow: changes requested, or *Unresolved comments* when it's approved but conversations are still open
  - green: *Ready to merge*, approved with every conversation resolved
  - blue: needs review

  Each row also shows resolved/total conversations and the time since the last push, title or body edit, or review. The current PR is highlighted, and links keep you on the tab you're on. Merged layers fold into one "N merged" row. The whole section collapses to a colored strip, and that setting is remembered. A PR outside any stack shows on its own.

- **One row per reviewer,** in a column beside the stack, most actionable first: *Changes requested*, *Re-requested*, *Review requested*, *Dismissed*, *Commented* and *Approved*. Requested teams get a row too. A glyph says what the reviewer said, in its colour: a green check for an approval, a yellow page with plus and minus for a change request, a speech bubble for a comment. The row's border says what counts now: green or yellow for a standing verdict, grey for none. A dismissed approval keeps its green check inside a grey border. A dashed border means they're asked to review, for the first time or again; a re-requested reviewer whose approval still counts has a green dashed border. The tooltip, and screen readers, say the rest: when they reviewed, what came before a re-request, a recent poke. The row's buttons (re-request, poke, dismiss) appear on hover or keyboard focus. With the stack collapsed, the reviewers shrink to their faces, each with the same glyph and border as a small badge.
- **Open, draft or closed:** the toolbar's end shows the pull request's state, coloured as GitHub colours it. A click opens its moves, each with its keys: convert an open pull request to a draft, mark a draft ready for review, close either, or reopen a closed one. It shows only when you may change the pull request, and not once it is merged.
- **Whose turn:** the toolbar under the stack starts with *Your turn* (filled) or *Their turn* (outlined) and why, after Gerrit's attention set. On your own pull request it is your turn for a merge conflict, failing checks, a change request you haven't pushed for, a reviewer to ask again after you pushed for their change request, threads where a reviewer spoke last, a review nobody is asked for, or merging; otherwise it waits for the reviewers it asks. On someone else's it is your turn while you're asked to review, when someone answered last in a thread you started, or when the author pushed since you requested changes. Bots' comments never decide a turn, and a draft waits for nobody. A reviewer whose threads the author answered last gets a dashed border and a speech bubble with the count: the next word is theirs. Someone else's turn with nothing to say hides the line.
- **Did they address it?** In the versions view, each open thread says whether the code it comments on changed since its first comment: *Code changed since your comment* (green), *Replied, code untouched* (blue) when the author answered instead, or *Untouched since your comment* (amber). FloHub diffs the version the comment was written on with the head, so a thread knows exactly whether its lines changed, a line put inside its range included; where that diff can't be had, GitHub's outdated mark decides. The toolbar under the stack counts the open threads the same way (`Threads: 2 changed · 1 untouched`), from GitHub's outdated marks alone.
- **Stale verdicts:** when the pull request has moved past a reviewer's standing approval or change request, their row shows the version it was given on (`v26`), and the tooltip says how far behind it is ("Approved v26 · 2 versions ago"). Two buttons appear on the row: one opens the versions view on what they haven't seen, from that version to the head; the other asks them to look again. That one opens a comment composed for them ("@alice Since your approval on v26 (`abc1234`): 3 files changed (+12 −4): `a.ts`, `b.ts`, `c.ts`. [See what changed](…)"), which you can edit before it's posted. Posting it also re-requests their review when they aren't asked already. The link opens the same range in the versions view, or plain Files changed without FloHub. The versions view's **Reviews** follows a reviewer the same way: a **What alice hasn't seen** button beside it compares their verdict's version with the head.
- **Poke:** a pointing finger on every reviewer who is currently requested (pending or re-requested), for users and teams. It removes and re-adds the review request, which makes GitHub send them a new notification within about a minute; asking again for a pending reviewer would do nothing. The PR timeline shows it as a removed and a new review request. A poked reviewer shows a grey finger instead of the button for an hour, with the time in the tooltip, remembered per browser. If re-adding fails, FloHub retries once and otherwise tells you to re-request them by hand.
- **Discussion:** the overview lists the comments people leave on the pull request as a whole: the text of each review (with its verdict) and general comments, newest first, with a link to each on GitHub. Inline review threads stay in GitHub's Comments panel. Comments since you last opened the pull request are marked "New", and the list shows those by default. The comment button in the toolbar counts the comments and the new ones, and opens the rest; on a first visit, "since your last review" counts instead. Long comments clamp to three lines with "Show more". Bots and stack tools' comments (CodeRabbit, Graphite's and gh-stack's stack notes) are hidden behind the bot button beside it. Comments keep GitHub's formatting (code, lists, links, quotes, tables, images, task lists and alert boxes), rebuilt from an allowlist so no script, handler or unsafe link reaches the page.
- **Which review counts:** a reviewer's verdict is their latest approval, change request or dismissed review. A later plain comment doesn't override it.
- **What's left out:** the PR author's own replies, unsubmitted drafts, and bots that only commented.
- **Viewed files in the tree:** on the Files changed tab, every file in the file tree gets a checkbox showing your Viewed mark, and clicking it marks or unmarks the file. Viewed files are dimmed, and so is an expanded folder once every file in it is viewed. A file that changed after you viewed it shows an amber dot. When the file's own Viewed checkbox is on the page, the tree clicks that one, so GitHub collapses the diff as usual. Otherwise the change goes through the API.
- **Line counts in the tree:** every file in the Files changed tree shows its added and deleted lines (`+12 −3`), right-aligned next to its Viewed checkbox, including files whose diff isn't rendered. A side with no lines is left out, and a binary file or a pure rename shows none. Hovering the counts spells them out.
- **Instant revisits:** the last overview of each pull request is kept in the extension's local storage for a week, up to 50 pull requests. A revisit shows it at once, marked as refreshing, until GitHub's answer replaces it. A layer you haven't opened yet shows its stack from another layer you opened, with reviewers loading. Changing the token clears the cache.
- **Compare versions after a rebase:** when the branch was force-pushed, the toolbar under the stack says how often, and its switch for what Files changed shows (**GitHub's diff**, **Since vN**, **Versions**) offers **Versions**. It replaces GitHub's diff with a range-diff of the whole pull request between any two of its versions: what the pull request itself changes in each version is diffed against the other, so what the base branch gained in between doesn't show up. It reads like any diff: a line only the newer version has is green, a line only the older one had is red, and where a line replaced a similar one, the words that differ are highlighted. The grey `+` or `−` beside the code, and the two line numbers, are what the pull request itself does to the line, so a line it adds the same way in both versions stays white. TypeScript, JavaScript, JSON and SQL get syntax colors. Folded context expands on click. The view's one-line toolbar picks the two versions: **From** and **To** name each in a few words (`v2 your review`, `v3 current`), and their lists show each version with its tags, its commit, who pushed it, its age, and its reviewers with their verdicts. They open on a click or the down arrow, and the arrows, Enter and Escape work in them. Neither offers a version that would put the newer side before the older. Between them, a strip draws every version from the base branch to the head, the compared range filled in and your last review marked under it. A version someone reviewed gets a wider slot with each reviewer's avatar and their verdict's icon (approved, changes requested, commented); a review since dismissed keeps the verdict it gave, its face greyed out. The many versions nobody reviewed shrink to ticks. Click a version to start the range there, or one past the range to end it there (Shift-click picks the newer side); hover it for its commit, pusher, age and reviews. **Reviews** follows one reviewer: its list shows each reviewer's verdicts version by version, and once you pick one, the strip shows only their reviews. Beside them, **Split** shows the diff side by side, **Comments** shows or hides the review threads, **Wrap** wraps long lines, and an icon opens GitHub's own compare. Drag the file tree's right edge to make it wider or narrower (or focus it and use the arrow keys, Home and End; a double-click restores the usual width); the width is remembered. Each file header shows the diffstat squares, whether the file was renamed, a button to copy its path and a link to the file at that version. Each file says what happened to it between the versions: *Changed*, *New file*, *Deleted*, *Restored*, *Newly changed* or *No longer changed*. A whole new or deleted file drops the markers and line numbers that would only repeat that. Files whose change is the same in both versions are listed collapsed. While **To** is the current version, each file header and each file in its tree also have GitHub's **Viewed** box, the same mark GitHub's own diff shows, so ticking it in either place ticks it in both. A viewed file starts folded and is dimmed in the tree, ticking a box folds the file, and a file that changed since you viewed it shows an amber dot. After a push resets the marks, and while **From** is the version you last reviewed, a button in the summary under the toolbar (*Mark 2 unchanged files as viewed again*) marks the unchanged files you had viewed as viewed again, since their change is the same as in the version you reviewed. GitHub keeps the marks for the current version only, so a range that ends at an older version shows no boxes, and files the pull request no longer changes never have one. It ignores hunks that only moved, but conflict resolutions show up. By default it compares the version you last reviewed, or else the previous one, with the current one.

  Versions are the heads before and after every force push, plus every commit someone reviewed. Plain pushes in between aren't recorded anywhere, so they only show up if someone reviewed them. They're numbered in the order they were the head, not by commit date. In a stack, an old version is diffed against the head the base branch had back then, so the parent's old commits don't leak into it. That still holds after the parent is merged and GitHub retargets the pull request. A file GitHub shows no diff for (binary, or too large) is marked *Can't compare* when its content differs, since that may only be the base's doing. GitHub lists at most 300 files per version; past that, files only one version lists are left out.
- **What changed since your review, in GitHub's own diff:** if you reviewed an older version of the pull request, Files changed highlights what is new or different since then, with the same rebase-aware comparison. A changed line gets an amber bar on its left, and you comment on it as usual. Where lines of the version you reviewed are gone, a red marker (`−2`) at the right end of the line before lists them on click (Escape or a click elsewhere closes the list). Each file header says whether the file changed since your review. The switch's **Since vN** counts the files and turns the highlights on; **GitHub's diff** takes them off. A button beside it lists the files the pull request no longer changes. Nothing is highlighted until you've submitted a review of a version older than the current one, and only the whole pull request's Files changed tab is highlighted, not a commit or a range of commits. The highlights are fetched again only when the head, the base or your latest review changes; otherwise they come from storage.
- **Jump to a comment's code:** in GitHub's comments panel on Files changed, a click on a comment's file link opens a small menu instead of GitHub's jump, which doesn't scroll there and sends an outdated comment to a single-commit view. **Changes since vN** opens the versions view from the version the comment was written on to the head, **Code at vN** shows that version's own changes, and **In the current diff** scrolls to the comment's thread or line in the diff on screen, greyed out when the comment is outdated. Each choice has an icon and a number key (1, 2, 3), and arrow keys, Enter and Escape work as in any menu. A modified click (⌘, Ctrl, Shift) still goes to GitHub. See [GitHub quirks](github-quirks.md).
- **Inbox:** the toolbar button's popup sorts the pull requests waiting for your review, those you reviewed and your own into sections, and each section into categories that say why a pull request is there. Every category keeps its heading, faded when empty, so the layout never shifts. **Your turn** starts with **Re-requested** in the attention colour, longest waiting first, since their author applied your review and waits on a quicker second look. Then come new review requests nobody has a verdict on yet, replies to you, new commits since your review, and your own pull requests to fix, to ask a review for, and ready to merge. **Their turn** splits into waiting for the author and waiting for reviewers. **Reviewed by someone else** holds the review requests another person already approved or rejected, since one human verdict is enough: an AI reviewer that asks a second person no longer puts a pull request on your turn. Bots' verdicts don't count. Being asked again by name still does. Then **Drafts**, and **Everything else**: the open pull requests the searches found that wait for nobody in particular, like one you approved. Its button loads every other open pull request of the owners and repositories the active profile shows, once, never on the timer, with a link to GitHub when an owner has more than fit. *Reviewed by someone else* and *Everything else* start folded, and only *Your turn* counts on the button's badge. The popup checks every 5 minutes. Each row says why it waits in tone-coloured words (*2 replies*, *New commits*, *Checks failed*, *Ask alice again*, *bob requested changes*, *Waiting for alice*), each explained on hover, then the layer's status when no reason says it already, the author, the repository, its place in its stack, resolved conversations and size. Rows also show everyone else's latest verdict as faces, each with the verdict's icon (who approved, who wants changes), and hovering them names each one; your own verdict stays a flag on the row. Arrow keys or `j`/`k` move between rows, and Enter opens one. Hovering or focusing a row shows its pin and snooze buttons (`p` and `s` on the focused row do the same). A pinned pull request sorts first in its category. A snoozed one leaves its section until the time you picked (for an hour, until tomorrow at 9:00, or until something happens on it), behind a *Show 1 snoozed* line.
- **Inbox views on a repository's pull requests:** signed in, the sidebar of a repository's pull request list (`/<owner>/<repo>/pulls`) gets a FloHub group below GitHub's own lists: **Your turn**, **Re-requested**, **Their turn** and **Reviewed by others**, each with the count of that repository's pull requests in it. They follow the inbox's rules and headings, which GitHub's search can't express: being asked again, replies to you, waiting for reviewers you re-requested. Re-requested shows under *Your turn* as well. A view opens in place of GitHub's list, and its rows pin and snooze as in the popup. The open view is kept in the address (`#flohub=rerequested`), so a reload keeps it; any of GitHub's own lists brings GitHub's list back. The views draw from the inbox, so they hold what the inbox's searches find, not every open pull request of the repository.
- **Profiles:** two named lists of repository owners, like *Work* and *Personal*, set up on the options page. Each owner goes on one profile or on both, and a repository added on its own can go elsewhere than its owner, and the popup's header switches which profile the inbox and the badge show, or all repositories. Switching is instant and keeps the other profile's pins and snoozes, since the inbox still fetches every repository.
- **Settings:** the options page sets up the token first, with a pill that says who it signs in as or why it doesn't, then lists the keyboard shortcuts and the repositories where only requests by name count.
- **Placement:** the overview sits inline below GitHub's PR header. In GitHub's newer header, that's below the tabs, so the PR number stays on the title's line. Once the header scrolls away, a compact pill appears at the bottom left with the stack strip, layer position and reviewer faces. It expands to the full overview (Escape closes it). The button beside it minimizes the pill to a slim tab at the window's left edge, so it doesn't cover the bottom of a long file tree; FloHub remembers the choice.

## Shortcuts

Graphite's shortcuts, on every pull request tab. They never fire while you type in a text field. The keyboard button at the end of the bar's toolbar lists them on the page, and the options page does too, both from the same list.

| Keys | Action |
|---|---|
| <kbd>⌘</kbd><kbd>⇧</kbd><kbd>↑</kbd> / <kbd>⌘</kbd><kbd>⇧</kbd><kbd>↓</kbd> (<kbd>Ctrl</kbd> outside macOS) | Go to the pull request above / below in the stack, on the same tab |
| <kbd>R</kbd> then <kbd>Y</kbd> | Approve right away, without a comment |
| <kbd>R</kbd> then <kbd>A</kbd> | Open the approve dialog to add a comment |
| <kbd>R</kbd> then <kbd>N</kbd> | Open the request-changes dialog; the comment is optional |
| <kbd>C</kbd> then <kbd>C</kbd> | Copy `gh pr checkout <number>` |
| <kbd>C</kbd> then <kbd>G</kbd> | Copy the pull request's link |
| <kbd>C</kbd> then <kbd>B</kbd> | Copy the pull request's branch |
| <kbd>]</kbd> / <kbd>[</kbd> | Go to the next / previous unresolved thread: in the versions view while it's open, in GitHub's diff otherwise |
| <kbd>F</kbd> | Go to the next file you haven't marked Viewed, in GitHub's diff or the versions view |
| <kbd>⇧</kbd><kbd>F</kbd> | Mark the file in view as Viewed, and go to the next |
| <kbd>V</kbd> | Show or hide the versions view |
| <kbd>R</kbd> then <kbd>R</kbd> | Re-request review from everyone whose approval or change request is on an older version |
| <kbd>P</kbd> then <kbd>P</kbd> | Poke every requested reviewer who hasn't answered yet, less those poked within the hour |
| <kbd>⌘</kbd><kbd>Esc</kbd> (macOS only) | Close the pull request, as on Graphite |
| <kbd>⌘</kbd><kbd>⇧</kbd><kbd>Esc</kbd> (macOS only) | Reopen it |
| <kbd>D</kbd> then <kbd>D</kbd> | Convert the pull request to a draft, or mark a draft ready for review |
| <kbd>1</kbd> <kbd>2</kbd> <kbd>3</kbd> | In the menu a comment's file link opens: pick a way to see its code |
| <kbd>?</kbd> | Show the list of shortcuts; <kbd>?</kbd> or <kbd>Esc</kbd> puts it away |
| <kbd>Esc</kbd> | Close a menu, a dialog or the versions view |

If you have a pending review with draft comments, every review shortcut submits it, so the drafts go out with your verdict, as with GitHub's "Submit review". In the dialog, <kbd>⌘</kbd><kbd>↵</kbd> submits and <kbd>Esc</kbd> cancels. GitHub refuses a change request without a comment, so an empty one is sent with an invisible zero-width space as its comment, which shows as an empty review.

Closing, reopening and the draft toggle act at once, without asking, and the message that confirms each one names the key that undoes it. A shortcut that has nothing to do, such as closing a closed pull request, says so instead. Windows keeps <kbd>Ctrl</kbd><kbd>Esc</kbd> and <kbd>Ctrl</kbd><kbd>⇧</kbd><kbd>Esc</kbd> for itself, so outside macOS closing and reopening go through the state button in the toolbar. GitHub binds no <kbd>D</kbd>, so both of the chord's keys are kept from the page.

Since <kbd>C</kbd> starts a FloHub shortcut, GitHub's own <kbd>C</kbd> shortcut (the commits menu on the Files changed tab) doesn't fire on pull request pages. <kbd>R</kbd> still reaches GitHub, so quote-reply on selected text keeps working.

Press a chord's first key (<kbd>C</kbd>, <kbd>R</kbd>, <kbd>D</kbd> or <kbd>P</kbd>) and wait a moment, and a hint lists what may follow, as on Graphite; the chord then waits for your next key however long you take. <kbd>Esc</kbd> or a click puts the hint away.

<kbd>]</kbd> and <kbd>[</kbd> match the character typed, so they work wherever a layout puts them: <kbd>⌥</kbd><kbd>6</kbd> and <kbd>⌥</kbd><kbd>5</kbd> on a German Mac, the third layer on Neo. They go on from the last thread they went to while it is still on screen, and from where you scrolled otherwise; past the last thread they start over. In GitHub's diff a thread GitHub keeps folded on its line, as it does while the comments panel is open, is unfolded, and with the panel open its card there scrolls into view and keeps a blue outline until the next thread. GitHub's diff only shows threads whose lines are still in the current diff, so the message also counts the outdated ones, which the versions view shows. From another tab, they open Files changed on the first or last thread. <kbd>R</kbd> then <kbd>R</kbd> and <kbd>P</kbd> then <kbd>P</kbd> act at once, like each reviewer's own buttons, and the message names whom they asked. GitHub binds no <kbd>V</kbd>, <kbd>F</kbd>, <kbd>P</kbd>, <kbd>]</kbd> or <kbd>[</kbd> on a pull request, so FloHub keeps them from the page. <kbd>?</kbd> shows FloHub's list in place of GitHub's own; it too matches the character typed, so <kbd>⇧</kbd><kbd>ß</kbd> on a German keyboard works.
